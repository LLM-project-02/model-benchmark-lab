## 사람 평가

### 방법

- **평가자·도구:** 평가자 1명이 구글 시트에서 경로별 출력에 `yes`/`no`를 적었고, 판단하지 않은 칸은 비워 두었습니다.
- **항목:**
  - 정책 준수: yes가 좋음
  - 의미 보존: yes가 좋음
  - 새 사실 추가: **yes가 문제 발생**
- **가림 여부:** 평가본에 `path` 열이 있었고, 경로 이름을 가리고 평가했는지는 기록되지 않았습니다.
- **원본과 대조:** `example_id`·`path`로 45행이 모두 원본과 하나씩 대응했고, 입력·상태·답변 불일치는 0건입니다.
  - 평가 열 밖의 차이는 시트 표시 형식(`True`→`TRUE`, 소수 자릿수 축소)뿐입니다.
  - 그래서 시간·토큰은 평가본이 아니라 `results.json`에서 읽었습니다. 평가값은 고치지 않았습니다.
- **비율의 분모:** 그 항목에 yes/no가 적힌 건수입니다. 빈칸은 no로 세지 않았습니다.

|---|---|---|---|---|---|
| 정책 준수 (yes 비율) | 14 | 6/14 (43%) | 10/14 (71%) | KcELECTRA만 yes 4, LLM 단독만 yes 0 | 없음 |
| 의미 보존 (yes 비율) | 12 | 7/12 (58%) | 9/12 (75%) | KcELECTRA만 yes 2, LLM 단독만 yes 0 | 2 (hate-01·hate-03, KcELECTRA 쪽 빈칸) |
| 새 사실 추가 (yes = 문제) | 14 | 3/14 (21%) | 3/14 (21%) | 한쪽만 yes 각 1 (LLM 단독 offensive-03, KcELECTRA offensive-02) | 없음 |

- **통계 검정:** 엇갈린 예제 수로 구한 정확 McNemar 검정 p값은 정책 준수 0.125, 의미 보존 0.5, 새 사실 추가 1.0입니다.
  표본이 작아 두 경로의 차이가 확인됐다고 볼 수 없습니다.
- **의미 보존의 다른 셈법:** 경로별로 따로 세면 LLM 단독은 14개가 모두 평가돼 9/14입니다.
  짝을 맞춘 12개 기준(7/12)과 다른 이유는, 제외된 hate-01·hate-03에서 LLM 단독이 모두 yes였기 때문입니다.

## 대표 실패 사례

1. **LLM 단독의 반복 생성으로 미완료 (hate-02)**
   - label은 offensive로 적었지만, answer에서 "폭풍이 왔다며 말하는 게 아니라,"를 반복하다 512토큰 한도에 닿았습니다.
   - JSON 스키마를 강제해도 반복 생성은 막지 못했습니다.
2. **LLM 단독이 문제없는 댓글을 고침 (none-02·none-04·none-05)**
   - 세 건 모두 offensive로 골라 고쳤고, 정책 준수는 no입니다.
     - none-04: "~하지마세요"가 "~를 피해주세요"로 바뀌어 의미 보존도 no입니다(메모: 명령조가 피해달라는 요구로 바뀜).
     - none-05: 문장부호만 사라졌습니다.
   - 같은 댓글을 KcELECTRA는 none(확신도 0.94~0.97)으로 판정해 원문을 그대로 두었고, 정책 준수는 yes입니다.
3. **분류기 오판이 그대로 이어짐 (KcELECTRA offensive-05·offensive-03)**
   - offensive-05: none(확신도 0.52)으로 판정돼 LLM이 원문을 그대로 두었습니다. 정책 준수는 no입니다(메모: 공격적인 어조가 충분히 완화되지 않음).
   - offensive-03: hate(0.92)로 판정됐고, LLM은 원문을 answer에 그대로 두고 다시 쓰라는 안내만 붙였습니다. 정책 준수는 no입니다.
   - 같은 두 댓글을 LLM 단독은 offensive로 골랐지만, 정책 준수는 역시 no였습니다.
4. **라벨이 맞아도 hate 정책을 따르지 않음 (KcELECTRA hate-05·hate-03)**
   - hate 정책: 혐오 표현을 지우고 남는 의견만 중립적으로 쓰고, 남길 의견이 없으면 게시하기 어렵다고 알립니다.
   - hate-05: 혐오 표현('○○들')이 든 원문을 answer에 그대로 두었습니다.
   - hate-03: hate로 판정됐는데, answer에는 "혐오 또는 차별적 표현이 아니며"라고 판정과 반대로 썼습니다.
   - LLM 단독도 두 건을 offensive·none으로 골라 정책 준수 no입니다.
   - hate-03의 평가자 메모: 기사 맥락 없이는 offensive와 hate를 구분하기 어려움.
5. **두 경로 공통의 생성 문제 (offensive-01·offensive-04)**
   - 분류 결과와 관계없이 같은 LLM이 뜻을 바꿨습니다.
     - offensive-01: '채널 돌렸다'는 관용 표현을 그 사람의 채널로 바꿨습니다.
     - offensive-04: 기자를 비판한 댓글을 기사를 써 달라는 요청처럼 바꿨습니다(메모: 판단 오류).
   - 두 경로 모두 의미 보존 no, 새 사실 추가 yes입니다.

## 해석과 한계

- **이 표본에서 확인된 것:** KcELECTRA + LLM과 LLM 단독을 비교하면 다음과 같았습니다.
  - KcELECTRA + LLM은 미완료가 없었습니다.
  - 정책 준수 yes가 더 많았습니다(10 대 6, 엇갈린 4개는 모두 KcELECTRA 쪽 yes).
  - 새 사실 추가는 같았습니다(3 대 3).
  - 처리 시간은 거의 같았고, 입력 토큰은 약 44% 적었습니다.
- **평가 조건의 한계:**
  - 개발 예제 15개(품질 비교 14개)를 평가자 1명이 평가했습니다.
  - 평가 기준 설명서, 두 번째 평가자, 평가자 간 일치도가 없습니다.
  - 경로 이름을 가렸는지 기록이 없습니다.
- **실행 조건의 한계:**
  - 경로당 1회 실행(온도 0.2)이라 반복 실행에 따른 변동은 재지 않았습니다.
  - LLM은 qwen3 4B 하나입니다. 서비스 기본 모델 `gemma4:e4b`나 상용 모델에서도 같은 경향인지는 모릅니다.
- **해석할 때 주의할 점:**
  - 두 경로는 프롬프트도 다릅니다(LLM 단독은 라벨까지 고름). 차이를 분류기만의 효과로 볼 수 없습니다.
  - 공통 파이프라인을 쓰지 않은 조건과 비교하지 않았으므로, 공통 파이프라인 자체의 효과에 대해서는 말할 수 없습니다.
  - 로지스틱 회귀 경로는 모델이 없어 세 경로 비교는 하지 못했습니다.
