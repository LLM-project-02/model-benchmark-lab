# review_rules01: 나쁜 답을 사람 검토로 보내는 규칙 두 가지

악성댓글 분류 + 순화 서비스에서 나쁜 답이 그대로 게시되지 않도록, 사람 검토로 보내는 규칙 두 가지를 개발 데이터로 고르고 최종 비교로 한 번 잰 실험입니다(2026-10-14).

- 결과 표: [review_rules_summary.md](review_rules_summary.md)
- 그래프: [review_rules_develop.png](review_rules_develop.png) (고르기), [review_rules_final.png](review_rules_final.png) (최종)

> **내용 주의:** 판정 결과 파일(`meaning_*.jsonl`)과 `final_routes.csv`에는 실제 댓글의 욕설과 혐오 표현이 그대로 들어 있습니다. 판정 모델이 쓴 이유 문장에도 원문의 표현이 인용돼 있습니다. 아래 예시는 가려서 적었습니다.

## 왜 했나

final02에서 고친 댓글 다시 검사(`answer_check`)는 나쁜 답(채점 4점 이하) 20개 중 7개만 잡았습니다. 놓친 13개를 원인별로 나누면 다음과 같습니다.

- **12개:** 분류 모델이 악플 3개를 none으로 잘못 골라, 고치지 않은 원문이 그대로 게시됐습니다(댓글마다 두 모델 x 2회).
- **1개:** 고쳐 쓰면서 뜻이 바뀐 답입니다.

처음에는 원인을 나눠 세지 않고 "뜻이 바뀐 답을 놓치는 것이 가장 큰 약점"이라고 설명했습니다. 잘못된 설명이었고, 바로잡은 뒤 두 규칙을 시험했습니다.

1. **확신도 규칙:** 분류 모델이 none으로 골랐어도 확신도가 기준값보다 낮으면 바로 게시하지 않고 사람 검토로 보냅니다. 큰 원인(분류 오류)을 겨냥합니다.
2. **뜻 검사:** 원문과 고친 댓글을 판정 모델에 함께 보여 주고, 원문의 대상과 평가를 지켰는지 판정하게 합니다. 처음 계획한 개선입니다.

## 앞 단계에서 고른 것이 쓰인 곳

- **분류 모델** KcELECTRA(`kcelectra-base_lr2e5_s44`): 확신도 규칙의 확신도를 낸 모델입니다. 학습 때 남긴 `validation_predictions.csv`를 그대로 썼습니다.
- **생성 모델:** 판정 대상인 고친 답은 local_models01(로컬 10개)과 final02(gemma4:e4b, gpt-6-luna)가 이미 낸 답입니다. 다시 생성하지 않았습니다.
- **채점:** 두 비교에서 Claude가 모델 이름을 가리고 매긴 점수를 정답으로 썼습니다(사람이 확인한 20건은 모두 동의).

## 조건

### 확신도 규칙
- **데이터:** validation 840건. 분류 모델이 none으로 고른 376건 가운데 정답이 악플인 것 67건, 정말 none인 것 309건
- **후보:** 기준값 0.50~0.99 (0.01 간격)
- **고르는 기준:** (놓친 악플을 잡은 비율 - 멀쩡한 댓글을 검토로 보낸 비율)이 가장 큰 값, 같으면 작은 값

### 뜻 검사
- **판정 대상:** 분류 라벨이 offensive나 hate이고 게시 불가 안내가 아닌 고친 답. none은 원문을 그대로 게시하고, 게시 불가 안내는 고친 문장이 아니라서 뺐습니다.
- **정답:** 채점의 '근거 없는 주장 없음' 점수. 0점 = 뜻이 바뀜, 2점 = 지킴, 1점 = 가벼운 변형(따로 보고)
- **개발:** local_models01의 고친 답 159개 (뜻 바뀜 83, 지킴 20, 가벼운 변형 56)
- **최종:** final02의 고친 답 28개 (뜻 바뀜 4, 지킴 11, 가벼운 변형 13)
- **판정 모델 후보:** 설치된 로컬 모델 10개 전부와 OpenAI `gpt-6-luna`(참고값, 서비스에는 쓰지 않음)
- **같게 둔 것:** 프롬프트(`steps/step08_connect_chain.py`의 `meaning_prompt`), temperature 0, 생각 단계 끔, 판정 JSON(이유, 판정)을 스키마로 강제, 최대 256토큰
- **프롬프트를 고친 것:** 개발 답 2개로 시험해 본 뒤 "원문의 일부가 빠졌어도 남은 내용이 원문과 같으면 뜻을 지킨 것이다"를 더했습니다. 채점의 '근거 없는 주장 없음'은 빠진 내용을 보지 않으므로 기준을 맞춘 것입니다.
- **고르는 기준:** 개발 답에서 (뜻이 바뀐 답을 잡은 비율 - 뜻을 지킨 답을 잘못 짚은 비율)이 가장 큰 로컬 모델, 같으면 빠른 모델

### 최종 (한 번)
- final02의 답 96개를 서비스 화면의 권장 조치 순서대로 나눴습니다. 처리 실패 → none이면 그대로 게시(확신도 규칙을 켜면 낮을 때 사람 검토) → 게시 불가 안내면 게시 보류 → 다시 검사나 뜻 검사에 걸리면 사람 검토 → 나머지는 순화 후 게시
- 나쁜 답(4점 이하) 가운데 자동으로 게시되지 않은 수와, 좋은 답(8점) 가운데 사람 검토로 간 수를 셉니다.

## 결과

### 고르기 (개발 데이터)
- **확신도 기준값: 0.93.** validation에서 놓친 악플 67건 중 55건(82%)을 잡고, 멀쩡한 댓글 309건 중 104건(34%)을 검토로 보냅니다. 전체 댓글로 보면 19%가 이 규칙 때문에 검토로 갑니다.
- **뜻 검사 판정 모델: `qwen3:4b-instruct-2507-q4_K_M`** (점수 0.23, 95% 구간 -0.33~0.64). 뜻이 바뀐 답 83개 중 52개를 잡고, 뜻을 지킨 답 20개 중 8개를 잘못 짚었습니다. 2위 qwen3.5:4b(0.22)와는 거의 같고, OpenAI(참고값)는 0.14였습니다.
- **모든 판정 모델의 95% 구간이 0을 포함합니다.** 이 프롬프트와 이 데이터로는 어느 모델도 뜻이 바뀐 답과 지킨 답을 확실히 가려내지 못했습니다.
- **함께 올라가는지:** 고른 판정 모델(3.0GB)과 생성 모델 gemma4:e4b(3.0GB)를 함께 올리면 둘 다 GPU에 100% 올라갑니다. 다만 노트북 GPU 메모리 8GB 중 약 7.4GB를 써서 여유가 거의 없습니다(nvidia-smi 7,593MiB / 8,151MiB).

### 최종 (final02 답 96개, 한 번)

| 규칙 | 나쁜 답(4점 이하)을 잡음 | 좋은 답(8점)을 사람 검토로 보냄 | 전체 답 중 사람 검토 |
|---|---:|---:|---:|
| 지금 (다시 검사만) | 7/20 | 2/54 | 12.5% |
| + 확신도 규칙 | 15/20 | 6/54 | 25% |
| + 뜻 검사 | 8/20 | 3/54 | 21% |
| + 둘 다 | 16/20 | 7/54 | 33% |
| + 둘 다 (뜻 검사를 OpenAI로, 참고) | 16/20 | 6/54 | 29% |

- **확신도 규칙:** none으로 잘못 고른 댓글 3개 중 2개(offensive-07, hate-05)를 잡아 나쁜 답 8개를 더 막았습니다. 대신 정말 none인 댓글 1개(none-07, 확신도 0.87)를 검토로 보내, 좋은 답 4개가 검토로 갔습니다. 확신도 0.96으로 none을 고른 offensive-03은 잡지 못했습니다.
- **뜻 검사:** 다시 검사에 걸리지 않은 답 8개를 새로 검토로 보냈습니다. 나쁜 답 1개(offensive-02 로컬 답변), 좋은 답 1개, 중간 점수(5~7점) 답 6개입니다. 다시 검사가 이미 뜻이 바뀐 답 8개 중 7개를 잡고 있어서, 더 잡을 수 있는 나쁜 답이 1개뿐이었습니다. 검토 비율은 12.5%(96개 중 12개)에서 21%로 늘었습니다.
- **뜻 검사의 오판 예:**
  - offensive-01: 원문의 비난 일부(인성 평가)를 빼고 나머지를 지킨 답(채점 8점)을 "뜻이 바뀌었다"고 짚었습니다. 프롬프트에 "일부가 빠졌어도 남은 내용이 같으면 뜻을 지킨 것"이라고 적었는데도 그랬습니다.
  - hate-04: 원문은 "야구나 잘해라" 뒤에 비하하는 말(○○○)이 붙은 댓글입니다. 비하하는 말만 지운 "야구나 잘했으면 좋겠다"(채점 8점)도 "뜻이 바뀌었다"고 짚었습니다. 이 답은 다시 검사에도 걸렸습니다.
- **응답 시간:** 뜻 검사는 고친 답 하나에 평균 1.54초(qwen3)가 더 걸립니다.

## 정답(채점)과 서비스 목적이 어긋나는 점 (사후 분석, 선택에는 쓰지 않음)

- 개발의 '뜻을 지킨 답' 20개 중 6개는 고친 댓글이 아니라 "이 댓글은 혐오 표현이므로 수정해야 합니다" 같은 안내문입니다. 채점에서는 지어낸 내용이 없어 '근거 없는 주장 없음' 2점이었습니다.
- 그런데 이런 안내문에는 "게시하기 어렵"이라는 말이 없어서, 화면은 이를 고친 댓글로 보고 그대로 게시합니다. 걸러야 하는 답입니다.
- 고른 qwen3와 OpenAI 모두 이 6개를 전부 "뜻이 바뀜"으로 짚었고, 잘못 짚은 것으로 셌습니다(qwen3 8개 중 6개, OpenAI 10개 중 6개). 안내문을 빼면 진짜 고친 댓글 14개 중 잘못 짚은 것은 qwen3 2개, OpenAI 4개입니다.
- 이 분석은 결과를 본 뒤에 한 것이라 모델 선택에는 쓰지 않았습니다.

## 한계

- 정답이 Claude의 채점입니다. 사람이 확인한 20건은 모두 동의했지만, 사람이 모든 답을 다시 채점한 것은 아닙니다.
- 최종 입력이 24건이고, 뜻이 바뀐 고친 답은 4쌍(답 8개)뿐입니다. 한두 개 차이는 우연일 수 있습니다.
- 원인을 찾느라 최종 입력의 확신도를 먼저 봤습니다(none으로 잘못 고른 3개 중 2개가 0.75, 0.80). 그래서 기준값은 validation으로만, 미리 정한 기준대로 골랐습니다.
- 확신도 규칙은 사람의 일을 늘립니다. validation 기준으로 전체 댓글의 약 19%가 이 규칙 때문에 검토로 갑니다.
- 뜻 검사의 판정 모델 후보는 이 PC에 설치된 모델이고, 프롬프트는 하나만 시험했습니다.

## 서비스 반영

2026-10-14에 두 규칙을 모두 서비스에 넣었습니다. 최종 비교에서 나쁜 답을 게시 전에 가장 많이 잡은 조합(20개 중 16개)입니다. 확신도 규칙만 넣는 쪽(15개, 사람 검토 25%)도 검토했지만, 둘 다 넣기로 정했습니다.

- **API:** `steps/step08_connect_chain.py`의 `review_classification`(확신도 규칙, `NONE_REVIEW_THRESHOLD = 0.93`)과 `review_meaning`(뜻 검사, 판정 모델은 `lesson_settings.MEANING_JUDGE_MODEL`)을 `steps/step10_serve_api.py`가 부릅니다. 응답에 `classification_check`와 `result.meaning_check`가 생겼습니다.
- **화면:** 세 검사(확신도, 다시 검사, 뜻 검사) 가운데 하나라도 걸리면 권장 조치가 "사람 검토"가 되고, 걸린 이유와 뜻 검사의 판정 이유를 보여 줍니다.
- **실험과 다른 점:** 서비스에서는 판정 JSON을 읽지 못하면 사람 검토로 보냅니다(실험에서는 표시하지 않은 것으로 셈). 고른 판정 모델이 형식을 틀린 판정은 개발 159개 중 1개, 최종 28개 중 0개였습니다.
- **치른 대가 (서비스에 넣은 뒤 실측):** 고쳐 쓰는 요청 하나가 평균 2.8초(생성 1.1초 + 뜻 검사 1.7초)가 됐습니다. 시연용 12건을 4개씩 동시에 보내면 10.7~11.6초에서 16~23초로 늘었습니다. GPU 메모리 사용량은 5,108MB에서 7,626~7,759MB(전체 8,151MB)로 늘었습니다. 자세한 표는 [bench01 README](../../README.md#서비스-확인-service_check01)에 있습니다.
